# `tasmota-import`

A build-time tool that converts Tasmota device templates into draft device profiles for the
TYWE2L-to-ESP32-H2 registry.

## Status, 14 August 2026

**Two pieces of it are built. The bulk importer in sections 4 to 8 is still specification only.**

| File | What it is |
| --- | --- |
| `extract_tables.py` | the section 3.1 extractor, implemented, with the self-tests it requires |
| `tables/tasmota-db56cd62aa45.json` | the generated tables, pinned to Tasmota `db56cd62aa455714e4a9a3043b8f835addf771a2` |
| `boards/tywe2l-h2.json` | the section 3.4 board definition: legs, test pads, unavailable pins |
| `decode_template.py` | decodes one or more templates and rules on TYWE2L fit. `--json` for tooling |
| `tests/test_decode_template.py` | 30 tests, including the owner's three verified devices |

```
python3 tools/tasmota-import/extract_tables.py                    # regenerate the tables
python3 tools/tasmota-import/decode_template.py '<template JSON>'  # decode and rule
python3 tools/tasmota-import/tests/test_decode_template.py         # run the tests
```

The decoder reports **driver architecture** (`pwm_direct`, `two_wire_led_driver`, `gpio_direct`,
`addressable_led`, `mixed`) separately from the pin verdict, because a device can fit the board
perfectly and still need firmware that does not exist. See
[`docs/device-inventory.md`](../../docs/device-inventory.md), which also flags that the profile
schema in `docs/flasher-and-registry.md` section 4.2 needs a first-class driver field before any
profile is written.

Not built: the corpus walker, the cross-checks, profile emission, the report and the rejection log.

Read [`docs/tasmota-import.md`](../../docs/tasmota-import.md) first. It contains the format
analysis, the measured corpus counts and the code-by-code conversion table that this tool
implements. It also contains the reasons for several rules below that look arbitrary in isolation.
Read [`docs/flasher-and-registry.md`](../../docs/flasher-and-registry.md) sections 3.2, 3.3 and 4
for the registry model, the profile blob and the trust tiers this tool feeds.

**This tool never publishes.** It emits candidate JSON files and a report. A human opens the pull
request, CI validates it, and a maintainer merges it.

---

## 1. Purpose and non-purpose

**Purpose.** Turn the community's accumulated knowledge of how Tuya devices are wired into a
starting point for our profiles, with enough provenance that a reviewer can check the work and a
future maintainer can replay it.

**Non-purpose.** This is not a bulk importer. It is a seeding and cross-checking tool. Its most
valuable output is the list of things it refused to convert and the list of corpus entries that
contradict each other.

---

**GPL-3.0-only**, matching Tasmota, because the tool reads and reproduces Tasmota's decode tables.

## 3. Inputs

### 3.1 Decode tables (required, pinned)

Generated by a separate, small extractor step (`extract-tables`) from a **pinned Tasmota commit**,
never from a floating branch. The extractor parses:

| Artefact | Source file |
| --- | --- |
| `enum UserSelectablePins`, **evaluated with `ESP32` undefined** | `tasmota/include/tasmota_template.h` |
| `enum LegacyUserSelectablePins` | `tasmota/include/tasmota_template_legacy.h` |
| `const uint16_t kGpioConvert[]` | `tasmota/include/tasmota_template_legacy.h` |
| `enum SupportedModulesESP8266` and `kModuleNames` | `tasmota/include/tasmota_template.h` |

Output: `tables/tasmota-<sha>.json`, checked into the repository.

```json
{
  "tasmota_commit": "…",
  "tasmota_commit_date": "2026-08-…",
  "extracted": "2026-08-13",
  "user_selectable_pins": {
    "esp8266": { "GPIO_NONE": 0, "GPIO_KEY1": 1, "…": 0 },
    "esp32":   { "GPIO_NONE": 0, "GPIO_KEY1": 1, "…": 0 }
  },
  "gpio_sensor_end": { "esp8266": 358, "esp32": 385 },
  "esp32_only_names": ["GPIO_KEY1_PD", "GPIO_WEBCAM_PWDN", "…"],
  "first_divergent_ordinal": 154,
  "legacy_user_selectable_pins": { "GPI8_NONE": 0, "…": 0 },
  "gpio_convert": [0, 1184, 1216, "…"],
  "supported_modules": [{ "base": 1, "enum": "SONOFF_BASIC", "name": "Sonoff Basic" }]
}
```

**Extractor hard requirements. Read section 1.3 of the analysis before writing this.**

- **Actually evaluate the preprocessor.** `UserSelectablePins` is a single enum containing inline
  `#ifdef ESP32` blocks, so it must be walked with a conditional stack, not with `#` lines
  stripped. Stripping them yields the ESP32 numbering, which decodes every ESP8266 template into
  plausible and wrong function names. This is the mistake that produced a first draft of the
  analysis claiming webcam pins on Tuya plugs.
- Terminate the enum at `GPIO_SENSOR_END`, not at the next `};`.
- **Fail on an unrecognised conditional.** At the commit surveyed the only directives inside the
  enum are `#ifdef ESP32` and `#ifdef USE_MODBUS_RELAY`; anything else must abort rather than be
  guessed at. `USE_MODBUS_RELAY` sits immediately before `GPIO_SENSOR_END` and shifts nothing, so
  ordinals are not build-flag dependent, but assert that rather than assume it.
- Emit **both** tables, ESP8266 and ESP32, and record the set of names present in only one of
  them.
- Evaluate each `kGpioConvert` entry as either `GPIO_NONE` or `AGPIO(NAME)` with an optional
  `+ n`, resolving `NAME` **against the ESP8266 table** (the file is inside `#ifdef ESP8266`).
  Anything else is a parse failure, not a warning. Abort if any name it references is
  ESP32-only.
- **Self-tests, and they must be part of the build**: `len(gpio_convert)` must equal
  `GPI8_SENSOR_END` (217 at the surveyed commit); the ESP8266 table must have 358 entries against
  the ESP32 table's 385, with 27 ESP32-only names and the first ordinal divergence at 154; and the
  three Old/New example pairs in the comment above `JsonTemplate()` in
  `tasmota/tasmota_support/support.ino` must round-trip exactly.

### 3.2 Corpus (required, pinned)

A local checkout of [`blakadder/templates`](https://github.com/blakadder/templates) at a **pinned
commit**, read from `_templates/`. The files are Jekyll collection items with YAML front matter and
no file extension.

**Do not use the published indexes.** `https://templates.blakadder.com/templates.json` is not
valid JSON (26 defects; the generator writes the `template` value unquoted and some entries contain
free text), and `list.json` is Markdown served as `application/json`
([`docs/tasmota-import.md` §2.1](../../docs/tasmota-import.md)). Worse than the parse errors, both
flatten every architecture-specific key to a single `template` field through a Liquid precedence
chain, so the encoding and the target architecture become unrecoverable from the field name. The
repository files keep the distinction.

**Do not mirror the corpus.** Read the files, take the `template` field and the metadata this tool
needs, and never reproduce blakadder's selection and arrangement wholesale
([`docs/tasmota-import.md` §6.2](../../docs/tasmota-import.md)).

Front-matter fields consumed: `title`, `model`, `category`, `type`, `standard`, `chip`, `link`,
`image`, `date_added`, and the template fields `template`, `template9`, `template_alt`,
`template9_alt`, `template32`, `templatec2`, `templatec3`, `templatec6`, `templates2`,
`templates3`.

### 3.3 Optional cross-reference

[`openbekeniot.github.io/webapp/devices.json`](https://openbekeniot.github.io/webapp/devices.json),
pinned, used **only** to look up a module part number by vendor and model. Its 37 ESP-family
entries carry **zero** pin maps ([`docs/tasmota-import.md` §2.1](../../docs/tasmota-import.md)), so
it must never be used as a pin source.

Two cautions. The repository has **no licence file of any kind**, so the default is all rights
reserved; treat a module name looked up there as a hint for a human rather than as data we
redistribute, and record it in `confidence.module_evidence` rather than copying the record.
[`tuya-cloudcutter.github.io`](https://github.com/tuya-cloudcutter/tuya-cloudcutter.github.io) has
better pin provenance still and the same licence problem, and in any case covers no ESP part, so it
is out of scope for this tool.

### 3.4 Configuration

```yaml
board: tywe2l-h2            # names the pad map below
available_pins: [4, 5, 12, 13, 14]      # ESP8285 GPIO numbers
# ESP8285 GPIO -> our board, under pin mapping v2. See docs/pin-mapping-v2.md.
# The numbering CROSSES OVER: ESP8285 12 -> H2 14 and ESP8285 13 -> H2 12.
# Never assume the two namespaces agree on a value.
pin_map:
  4:  { pad: 5, h2_gpio: 11 }
  5:  { pad: 4, h2_gpio: 10 }
  12: { pad: 2, h2_gpio: 14 }
  13: { pad: 3, h2_gpio: 12 }
  14: { pad: 1, h2_gpio: 13 }
allowed_base: [18]
variants:                                # from the firmware build, cluster sets
  onoff:   [OnOff, Identify, Groups, Scenes]
  dimming: [OnOff, LevelControl, Identify, Groups, Scenes]
  colour:  [OnOff, LevelControl, ColorControl, Identify, Groups, Scenes]
```

The pad map is the only board-specific data. A future board with more pads changes this file and
nothing else.

## 4. Pipeline

Nine stages. Each records why it dropped a record; nothing is discarded silently.

1. **Read.** Parse front matter. Reject files with no template field or unparseable YAML.
2. **Select the template field.** Prefer `template9` over `template` when both exist, and keep
   the other for stage 8. `*_alt` fields become separate candidates flagged
   `alternate_revision`. Any `template32` / `templatec*` / `templates*` field routes the record to
   the `other-platform` bucket and stops.
3. **Detect the encoding**, using Tasmota's own test verbatim: 13 array elements **and** every
   value below 256 means legacy. Anything else with a 14-element array is modern ESP8266. Any
   other length is `other-platform`.
4. **Decode.**
   - Legacy: index `gpio_convert`; out-of-range becomes free. Then take `FLAG & 0x0F` and, if
     non-zero, synthesise the ADC0 slot as `AGPIO(GPIO_ADC_INPUT + flag - 1)`.
   - Modern: the value is already packed. Rewrite `1` to "free", matching
     `JsonTemplate()`'s `AGPIO(GPIO_NONE) + 1` handling.
   - Split each value into `function = value >> 5` and `index = value & 31`; look the function up
     in `user_selectable_pins`. An unknown ordinal is a **hard failure**, never a free pin.
5. **Expand slots to physical GPIOs** using the ESP8266 table: slots 0 to 5 map to GPIO0 to GPIO5,
   slot 6 to GPIO9, slot 7 to GPIO10, slots 8 to 12 to GPIO12 to GPIO16, slot 13 to ADC0.
6. **Filter.** Every assigned pin must be in `available_pins`. `BASE` must be in `allowed_base`.
   At least one output role must exist.
7. **Map** each code through the conversion table in
   [`docs/tasmota-import.md` §3.2](../../docs/tasmota-import.md) to a role, an active level, a
   pull requirement and an outcome of A, H or X. Any X is fatal for that record. Any H adds an
   entry to `confidence.open_questions`.
8. **Cross-check.** Compare against the other template field on the same file, against other
   corpus entries with the same normalised `title` + `model`, and against OpenBeken for a module
   name. Set `confidence.corpus_agreement`.
9. **Emit** profiles, the report, and the rejection log.

Field notes that are easy to get wrong:

- **`gpio` is our ESP32-H2 number** under pin mapping v2, already translated. `esp8285_gpio` and
  `pad` are kept for the reviewer and for debugging. The firmware only ever reads `gpio`.
  **The two GPIO namespaces cross over** (ESP8285 12 to H2 14, ESP8285 13 to H2 12), so a record
  where `esp8285_gpio` and `gpio` happen to match is a red flag, not a reassurance. Test on `pad`,
  which equals the leg number and is stable across any future remapping.
- **`index` is zero-based** in our schema and one-based in Tasmota's display. `GPIO_REL1#2` in the
  documentation is packed value 225, decodes to index 1, and emits `"index": 1`.
- **`from`** must be present on every pin. It is what makes a review possible and what lets a
  future table correction be replayed.
- **`follows`** captures Tasmota's LED-mirrors-relay pairing by index. Dropping it wires the wrong
  LED to the wrong relay on multi-relay devices.
- **`confidence.state`** is always `"imported"` on emission. This tool can never produce
  `reviewed` or `verified`.
- **`duplicates`** lists every other corpus entry that produced a byte-identical pin map, so one
  reviewed profile covers many products. In the measured corpus, 235 clean records collapse to 124
  distinct pin maps ([`docs/tasmota-import.md` §3.4](../../docs/tasmota-import.md)).
- **`prose_copied` is always `false`** and the tool must make that true by construction: it reads
  the `template` field and the structured metadata, never the body prose or the images.

### 5.3 `confidence.open_questions`

Free-text strings, one per unresolved decision, and a profile with a non-empty list cannot be
promoted past `imported`. The generated set:

| Trigger | Question emitted |
| --- | --- |
| always | `module not identified: confirm the part number on the board` |
| any `SWT` code | `switch mode: follow, toggle, or push-button?` |
| any PWM | `PWM frequency not specified in the template` |
| any PWM | `dimmer range (minimum brightness) not specified` |
| 2+ PWM channels | `channel-to-colour assignment not specified` |
| 2 or 5 PWM channels | `colour temperature range (mireds) not specified` |
| any `BUZZER` | `no Matter cluster for a buzzer: bind to Identify or drop?` |
| any `INPUT` | `input semantics unknown: Boolean State or drop?` |
| any sensor code | `sensor driver and firmware variant not selected` |
| `corpus_agreement` is `conflicting` | `corpus disagreement: <n> sources give different pin maps` |
| `CMND` present | `template carries a CMND backlog, review it: <text>` |
| non-zero modern `FLAG` | `unexpected non-zero FLAG in a modern template: <value>` |

### 5.4 Report

`report.md` opens with the attribution notice, then:

- Corpus totals: files read, unparseable, by platform, by encoding.
- Pin-fit table with the same columns as
  [`docs/tasmota-import.md` §2.2](../../docs/tasmota-import.md), so drift is visible at a glance.
- Outcome counts: clean, needs-decision, cannot-support, empty, and distinct pin maps in each.
- Breakdown by normalised category.
- **The conflict list**, in full. This is the section a reviewer actually reads.
- **The TuyaMCU list**, named, so a user who owns one gets a real answer.
- The full rejection tally by reason code.

### 5.5 Rejection reason codes

Stable strings, because they go in `rejected.jsonl` and in the report, and because CI asserts on
them.

| Code | Meaning |
| --- | --- |
| `no-template-field` | front matter carries no template key |
| `unparseable-template` | the value is not JSON |
| `other-platform` | ESP32-family template field or array length |
| `ambiguous-encoding` | 13 elements with a value above 255, or any other undecidable case |
| `unknown-code` | a function ordinal not present in the decode table |
| `esp32-only-code` | the decoded name exists only in the ESP32 arm of the enum, which means the table or the routing is wrong |
| `pin-not-available` | uses a GPIO the board does not surface; the list is included |
| `adc0-used` | legacy `FLAG & 0x0F` non-zero, i.e. needs TOUT |
| `base-not-generic` | `BASE` is not 18; the decoded module name is included |
| `tuyamcu` | a special case of the above, `BASE` 54 or the Tuya pins present |
| `unsupported-code` | a code marked X in the conversion table; the code name is included |
| `no-outputs` | nothing assigned, or only inputs |
| `duplicate-function` | the same function and index on two pins |
| `non-contiguous-index` | relay, button or PWM indices with a gap |
| `orphan-led-index` | `LED#n` with no `REL#n` |
| `corpus-conflict` | sources disagree; emitting would be unsafe |
| `no-variant` | the required cluster set matches no configured firmware variant |

`tuyamcu` is separated from `base-not-generic` deliberately. It is the largest single class of
"looks importable and is not" ([`docs/tasmota-import.md` §4.1](../../docs/tasmota-import.md)) and
users deserve to be told which device they have rather than being handed a generic failure.

## 6. Failure modes, and what the tool does about each

The ones that matter, in order of how much damage they cause.

| Failure | How it bites | Defence |
| --- | --- | --- |
| **Decoding a modern value with the legacy table, or the reverse** | Silently produces a plausible-looking but completely wrong pin map. The worst possible outcome, because nothing downstream can detect it | Use Tasmota's exact detection test. Refuse `ambiguous-encoding`. Record `source_encoding` in every profile so a mistake is auditable after the fact |
| **Using the ESP32 arm of `UserSelectablePins` for an ESP8266 template** | Same, and just as invisible | Extractor asserts it parsed the `#ifdef ESP8266` arm; the round-trip self-test in §3.1 catches it |
| **Ignoring `BASE`** | Emits 32 TuyaMCU profiles that pass every pin check because 24 of them use no pins at all ([`docs/tasmota-import.md` §1.5](../../docs/tasmota-import.md)) | `allowed_base: [18]`, and a named `tuyamcu` rejection |
| **Ignoring the legacy `FLAG`** | Silently drops an ADC0 sensor on 178 legacy templates and claims the device fits | `adc0-used` rejection |
| **Reading only `template9`** | Loses 171 of the 235 clean profiles, because the old corpus is nearly two thirds of the value ([`docs/tasmota-import.md` §3.4](../../docs/tasmota-import.md)) | Both eras are first-class; the encoding test decides, not the key name |
| **Relay polarity inverted** | **Energises mains at boot.** The one that can hurt someone | `REL1` versus `REL1_INV` is carried faithfully, `boot_state` is always emitted as `off`, and the firmware holds pins as inputs until the profile CRC passes ([`docs/tasmota-import.md` §5.4](../../docs/tasmota-import.md)) |
| **Dropping the instance index** | Wrong LED follows wrong relay on multi-relay devices | `index` and `follows` are mandatory; `orphan-led-index` check |
| **Trusting a single corpus entry** | 38 of 64 second opinions disagree ([`docs/tasmota-import.md` §2.4](../../docs/tasmota-import.md)) | `corpus_agreement`, and `corpus-conflict` blocks emission |
| **Treating pin compatibility as module identity** | The user's device has a TYWE3S and a different footprint | `module_identified: false` on every emitted profile, and the installer warning |
| **Executing or interpreting `CMND`** | Arbitrary Tasmota commands from an unreviewed source | Never parsed for meaning. Copied verbatim into an open question |
| **Corpus or Tasmota drift** | Numbers move, tables change under us | Both inputs pinned by commit SHA and recorded in `provenance` |
| **Emitting a profile no firmware variant can run** | User flashes and the device boots into recovery | `no-variant` check against the configured variant list |
| **Silent partial output** | A crash halfway leaves a half-imported registry | Write to a temporary directory and rename at the end. Non-zero exit on any internal error |

## 7. Modes

| Mode | Behaviour |
| --- | --- |
| `report` (default) | Runs the whole pipeline, writes the report and the rejection log, **emits no profiles**. This is what runs in CI |
| `emit --outcome=clean` | Additionally writes profiles for records where every code is outcome A |
| `emit --id=<source_id>` | One record, including outcome H, printing each open question and taking the answer interactively |
| `verify` | Re-runs the pipeline over profiles already in the registry and reports where the current tables would produce a different answer. Run after any table update |
| `extract-tables` | Regenerates §3.1 from a pinned Tasmota commit |

`report` mode existing separately, and being the default, is the whole safety design in one line:
the easy thing to run produces information, and producing profiles takes an explicit flag.

## 8. Acceptance criteria

The implementation is done when:

1. `extract-tables` self-test passes: `len(gpio_convert) == GPI8_SENSOR_END`, and Tasmota's own
   Old/New example pairs round-trip.
2. `report` over the pinned corpus reproduces the counts in
   [`docs/tasmota-import.md` §2.2 and §3.4](../../docs/tasmota-import.md): 2,539 ESP8266
   templates (1,640 legacy, 899 modern), 902 pin-fitting, 774 also `BASE` 18, and
   235 / 440 / 90 / 9 across the four outcomes.
3. `conflicts.jsonl` contains the 38 both-fields disagreements and the 78 same-`NAME` disagreements.
4. Every emitted profile validates against the registry JSON Schema and carries a complete
   `provenance` and `confidence` object.
5. `emit --outcome=clean` produces 124 distinct pin maps, each listing its duplicates.
6. Every rejection carries one of the §5.5 codes and a human-readable explanation.
7. `verify` is idempotent against freshly emitted output.

## 9. Explicit non-goals

- Converting ESP32-family templates. The array indexing differs per variant
  ([`docs/tasmota-import.md` §1.2](../../docs/tasmota-import.md)) and no ESP32 Tuya module is in
  scope for this board.
- Converting TuyaMCU, serial-bridge, IR, RF, addressable-LED or serial-LED-driver devices.
- Importing prose, images or any other creative content from the corpus.
- Publishing. Ever. See §1.
